# 巫师牌：美术与UI设计需求清单

更新日期：2026-10-04。基线：程序 `0.4.2-dev` / 规则 `0.2.2` / 卡池 `0.1.0`。

本轮按用户要求整理三个交付目标：**完成卡牌UI设计、完成场地美术设计、完成卡牌操作UI设计**。本轮已交付190个独立UI PNG及SVG源稿、46张设计稿与13组流程，并补齐9幅插画；[资源画廊](../assets/art/design/v1/index.html)和[接入规范](../assets/art/design/v1/integration.md)可直接查看。设计与导出完成不等于新UI已在客户端接入或通过真人验收。

> 接入更新：0.4.2-dev 已接入13张插画与主要UI皮肤，增加低对比背景、拖动使用、目标/成本拖放及手牌整理。43项测试和完整拖放重放通过。以下设计交付记录保留作为资源依据，真人体验验收仍待进行。

基础均衡与扩展均衡共用插画，通过基础保护标识区分。奥术圆环的附着角标需可单独点击，不能只作为卡框装饰。

卡牌选中时采用两个独立组件：**详情面板负责阅读，卡牌附近操作条负责执行**。详情面板固定在场地右侧，操作条跟随所选卡牌位置；两者通过相同卡名/选中标识对应。切换所选卡牌时同步更新，无合法操作时仍可查看详情。详情关闭按钮属于查看控制；当前实现关闭会清除选择，不能把它设计成执行卡牌效果的按钮。

- 交付5种展示类型在手牌、场内、详情中的示例，覆盖双段费用、长规则文本、基础保护和符文附着。

- 类型色、稀有度色与操作高亮各有独立位置和语义，不互相覆盖。

### 3.2 场地设计完成标准

- 空场和复杂场面都能区分区域，阵体2跨槽和其解析法术的归属一目了然。
- 双方区域对称，标签正向；当前操作者与本方/对方身份明确，换手后不会因配色误判。
- 荷载等于上限仍安全；接近上限可预警，严格超过才是过载，设计不能误报败北。
- 独立底图、框体与标签可接入；不将包含假文字、假卡牌、假数值的整张概念图作为运行背景。
- 16:10基准与其他窗口比例下验证缩放、留边、长文本和卡牌密集场面；UI设计稿标出可伸缩区域。

### 4.2 必须覆盖的交互流程稿

| 场景 | 流程与设计重点 |
|---|---|
| 选中与查看 | 点击卡牌→右侧显示该卡详情、卡牌附近独立显示合法操作→切换卡牌同步更新；没有合法操作时保留详情，不显示空操作条 |
| 设置/替换阵法 | 手牌阵法→菜单分别展示设置/替换→需要替换时选合法扩展阵法→确认；基础阵法保护明确 |
| 开始解析 | 手牌法术→开始解析→选择合法宿主阵法→确认解析费用与荷载→显示解析状态 |
| 准备施法与额外成本 | 已解析法术→准备施法→需要时选目标→需要时选弃牌手牌→汇总确认→进入言灵响应 |
| 使用行动 | 手牌行动→使用→需要时选目标→确认费用/自身负担；不出现行动次数耗尽提示 |
| 预置/触发言灵 | 手牌言灵→预置→确认；响应时换手遮挡→接手→选择预置言灵或跳过→确认 |
| 附加/拆除符文 | 手牌符文→附加→选择合法宿主→确认；点击宿主上的符文角标可查看并拆除 |
| 施法阶段选择 | 提示选择待施放法术→选卡/操作→确认；待施放与持续生效视觉不同 |
| 结束弃牌 | 标出需弃数量→选择手牌→确认→继续至任务完成；与准备施法的弃牌成本有不同提示 |
| 临时荷载移除 | 列出来源、可移除数值→逐项选择→更新剩余任务；与绑定荷载区分 |
| 触发顺序/多余法术 | 展示当前决策与合法候选→选择并确认；候选较多时支持滚动 |
| 取消与重新选择 | Esc/关闭/取消回到检查状态；确认提交前游戏资源不变化；不把取消UI选择等同于取消法术准备 |
| 终局与重开 | 展示结果/原因→保存并开始新对局→换手遮挡；未接手不揭示私有信息 |

玩家目标按当前操作意图体现，不引入一个代码尚未支持的可点击玩家头像目标步骤。建议在最终确认中明确“自己/对手”；卡牌目标才进入现有高亮卡牌选择流程。

### 4.3 操作UI完成标准

- 上述流程有连续状态稿和交互注释，覆盖无目标、单目标、额外成本和强制决策。
- 点击源卡、选择候选、选定目标、最终确认的视觉层级各不相同；滚动后高亮与选择仍对应同一卡牌。
- 详情面板与操作条分别交付；包含同时展示、无合法操作、目标选择、额外成本及最终确认的状态稿。详情为只读信息区，执行按钮始终位于独立操作组件。
- 操作条在场地边缘有避让示例；右侧详情面板不与操作条重叠，弹窗不能同时要求点击被它完全遮住的目标。
- 换手窗口不泄露手牌、菜单或日志；准备被言灵取消后仍能读懂法术保留与资源变化。
- 基于既有点击与确认流程完成设计；拖拽施法、目标指引和手牌整理已作为0.4.2-dev新增交互接入，仍保留原有点击入口。

## 5. 统一交付规范与设计验收

### 5.1 设计稿与资源包

- **设计源文件**：可编辑、分层；卡牌模板、场地组件、操作组件分别组织；元素和状态有稳定名称。
- **设计稿**：按1600×1000基准交付；至少包含卡牌三种展示规格、初始/复杂场地，以及第4.2节操作流程状态稿。
- **导出资源**：卡框、卡背、图标、按钮、区域框、背景分开导出PNG；数值、卡名、规则、区域标签由程序显示。可由代码绘制的组件可交付尺寸/颜色/边距规范，无需强制位图化。
- **接入说明**：组件尺寸、锚点、内边距、可伸缩边与九宫格切分（如采用）、像素单位、状态优先级；最近邻采样，避免像素边缘模糊。
- **资产清单**：资产ID、文件路径、版本、用途、尺寸、透明度要求、来源/许可；现有卡图继续使用 `assets/art/runtime.json` 按卡牌ID映射。
- **像素约束**：先确定统一栅格与色板再批量制作；四张现有插画仍是像素风试制成果，不宣称已通过严格限色、固定网格或二值透明度精修。现有插画实际1448×1086、4:3，不据此规定完整卡面比例。
- **字体**：延续现有 Noto Sans CJK SC，像素边饰不能挤压中文和长规则文本；不得把概念图生成文字作为正式文字。

建议新资源分别放在 `assets/art/ui/cards/`、`assets/art/ui/board/`、`assets/art/ui/interaction/`；这些目录是交付建议，新增UI纹理仍需程序映射和绘制接入。已有四张插画位置保持 `assets/art/cards/`。

### 5.2 制作顺序

1. **统一视觉与组件规范**：确定卡框、边框、资源图标、按钮和高亮的共用语言；先用四张现有插画制作卡牌模板。
2. **完成卡牌UI与场地美术主稿**：以当前布局产出初始和复杂场面；同时验证跨槽阵法、附着符文与缩略图。
3. **完成卡牌操作UI流程稿**：围绕已有菜单、目标、额外成本、确认和换手实现，复用前两项组件。
4. **导出并程序接入**：图片导出与组件规范齐备后接入；确认已实现功能不因皮肤改造受损。
5. **实机验收并补齐配套插画**：三项设计分别验收；9张缺失插画持续跟踪，不把全部卡池插画完成当作开始UI接入的前置条件。

三项均为本轮必交付，不把操作流程、换手遮挡或复杂场面设计留作后续装饰阶段。音效、品牌图标、卡包/商城、额外角色与动画特效不作为本轮完成条件。
