# WizardCard 前端精修评估与计划

日期：2026-10-10。评估基线：本地工作树，HEAD `fc1db9b`；包含当前尚未提交的美术需求和 C 像素资源包。用户本轮提供的主菜单、卡组编辑器两张图片作为风格参考。本轮交付评估与计划，没有修改前端、规则、卡池或原美术文件。

## 1. 结论

当前 Godot 前端是可靠的展示与交互基础，但视觉完成度还处于原型阶段。主要问题是设计基准、组件材质、卡牌信息排版与战场构图没有形成同一套规范。提高默认分辨率有必要，同时需要重新分配画面空间；已经能渲染 1080p，并不等于已经按 1080p 完成设计。

建议沿用现有 Godot 与 C++ 桥接、展示模型、资源 ID 和隐私边界，分批替换视觉层。先完成主菜单、卡牌与复杂战场的共同样板，再量产美术与页面。资源数量、通过自动检查和达到参考图的美术质量分别验收。

## 3. 两张参考图如何转为规范

| 参考 | 应采用的视觉与布局原则 | 需要按本项目重新设计的部分 |
|---|---|---|
| 主菜单图 | 细密像素奇幻；金属金边与青色宝石；石拱、城堡、月光、火焰形成冷暖层次；品牌是主要视觉；主按钮有明确外形与材质 | 分离环境、Logo、按钮、文字、局部动画；底图不能包含可点击文字；菜单入口按实际功能状态接入 |
| 编辑器图 | 左侧大卡详情，中间卡组，右侧卡池；头部信息与底部保存区稳定；工具、筛选和翻页各有不同外形；密集信息具有清晰分区 | 图中 30/30、基础阵法和旧类型不作为新版规则规格；新版按正式审定的 40 张主卡组与 10 张副卡组设计 |

风格定位为“细密像素奇幻”，重点是像素簇、材质与照明的一致性。菜单可以拥有较多环境细节；战场中央降低对比与纹理密度，把最高对比留给卡牌、合法目标、选中状态和关键资源。装饰主要放在边缘、标题与主操作上，阅读区保持安静。

两张参考图没有定义对局场地，因此需要增加空场与复杂场面的 1920×1080 战场设计稿。参考图用于验证共同视觉语言，不能把编辑器的密集边框直接套到战场每个空位。

## 4. 1920×1080 布局与排版

1. 将 1920×1080 作为主设计画布和新用户的首选显示尺寸。实际初始窗口受显示器可用区域约束，不让窗口超出屏幕；已有用户保存的合法尺寸继续生效。
2. 同步检查 project.godot、显示设置回退、设置页选项和原生 Settings 默认。原生默认同时服务旧客户端，实施时核对共享行为后决定是否采用 Godot 专用首启默认，避免附带改变旧客户端体验。
3. 第一版保留按实际可用尺寸布局的 Control 重排方式；背景按比例 cover。1280×720 通过减少网格列数、折叠详情与次要工具、浏览阵法行适配，不把 1080p 整页缩小后仍塞入相同文字。
4. 定义统一的 8px 间距基准、24–32px 页面外边距、48–56px 普通操作高度；菜单主按钮可用 64–80px 高度。所有尺寸先作为样板参数，在引擎中确认。
5. 1080p 正文目标 18–22px，紧凑辅助字段 16px；720p 阅读正文至少 16px、辅助至少 14px。中文采用实时字体排版，标题与正文分级，装饰字仅用于 Logo 或短标题。
6. 卡框为名称、费用、类型/速度、稀有度、状态分别提供安全区。不同显示档位独立配置字段；小卡呈现必要信息与状态，详情显示完整效果，不靠进一步缩小文字解决冲突。
7. 像素边框、图标采用对齐像素的目标尺寸与对应源稿；原插图的采样单独处理。UI、字体和图案的放大策略分别验证，避免统一 nearest 或统一 linear。

编辑器的 1080p 灰盒起点：32px 外边距，两处 24px 间隔；详情列 360px，主/副卡组列 960px，卡池列 488px，总计 1920px。头部 112px、底部 64px，中部 904px；中央主/副卡组用页签或分区，右侧卡池负责搜索、筛选与浏览。列宽和卡牌尺寸以真实长名称、40/10 牌表和筛选结果验证后锁定。

## 5. 美术精修工作流

### 制作要求

- 使用 Pixelorama 或等价像素编辑器手工调整像素簇、轮廓、材质、高光与投影，交付分层源稿；将 PNG 打开再导出不算精修。
- 先完成一个金边主按钮、一张解析法术卡框、一组资源图标、一处阵法锚点和战场材质样块。用同一组样板验证菜单、构筑和战场，再扩展变体。
- 建立共享调色板与材质表；金属、石材、宝石、纸面各有固定光源和明暗层级。旧资源的严格 32 色限制应在样板中重新评估，不让颜色数量替代质量验收。
- 四档卡框分别在实际显示尺寸重绘或修整，不能仅将详情卡缩小得到所有小卡。正文、卡名和动态数值继续由 Godot 绘制。
- 原 30 张插图先保留 ID 与文件，逐张检查像素密度、边缘与色调一致性；确有不协调者单列第二批，不把全部插图重绘设为首批前置条件。
- 原始文件留存，新批次使用独立版本目录；精修资产接入稳定 ID，更新尺寸、安全区、九宫格、采样、帧信息、来源和哈希。

建议交付目录：

```text
assets/art/godot-2d-v2/
  source/pixelorama/       # 分层 .pxo 源稿
  palettes/               # 共享调色板
  export/                 # PNG 与序列帧
  manifests/              # ID、来源、尺寸、切片、动画与哈希
  previews/               # 实际尺寸样板和对比图
```

## 7. 对局场景重新设计

建议第一套场地为与菜单同世界观的“城堡露台奥术竞技场”：低对比石质主战面，上下对抗布局，边缘保留金属、符文和局部暖光。场地保持 2D、接近俯视的可点击布局，透视与光影只服务层次。

- 背景拆为远景环境、石质主战面、边缘装饰、局部环境动画、投影/光效；卡牌区域保留低频纹理，避免与插图竞争。
- 沿用左阵法锚点、右横向解析行；副卡组入口在牌库上方，灰烬独立入口。空环位采用轻量刻纹/符号，悬停或操作时增强，避免每个空位都显示常驻面板。
- 顶部与底部安排双方必要资源；中央组织施法与连锁反馈，底部手牌提高到可读尺寸。阶段/优先权用独立控件，详情、配方、日志按需展开。
- 宿主关系使用局部连线与选中强调；阵法过多按行浏览或展开当前组。环位过多保持最低卡牌和命中尺寸，通过区域浏览到达全部位置，不继续压缩直至忽略绘制。
- 多手牌使用受控重叠/展开，悬停抬起与点击区域一致；需要保证最后一张、长卡名和拖动返回仍可操作。
- 0/1/7/12 环位、五阵法、大手牌和长连锁都做设计状态稿；数量来自投影，不把它们写成新的规则上限。
- 保留单画布绘制卡牌的方式，先分离布局参数、命中计算和视觉皮肤。必要时用少量 CanvasItem 分层处理背景、框体、插图与效果的采样，不为每个空位创建按钮。
- 动画作用在视觉层；点选/拖动不支付费用，最终确认沿用精确上下文，隐藏身份先清除再进入贴图与特效。

新增 HUD 与连锁状态以 C++ 会话投影为唯一依据。规则尚未接入时使用显式展示夹具验视觉，真实动作与功能验收仍遵守 R01/R04/F02 等既有依赖。

| 5. 页面扩展与真实接入 | P2 | 40/10 构筑、对局配置、教学、房间、结果及异常状态；真实资源/优先权/连锁 | 视觉稿与实际功能分别记录；数据来自原生服务，保存/取消/错误能恢复 | 视觉稿可提前；功能接入依赖 F02/F03 与审定内容 |
| 6. 演出与实机验收 | P2 | 关键事件动画音效、精简模式、DPI/输入、性能与发布资源检查 | 三种尺寸无重叠；IME/DPI 实测；隐私/决策回归通过；约定硬件复杂场面达到 1080p/60fps | 静态视觉稳定；事件接入依赖真实会话 |

首个可评审交付建议限定为：**三类页面的 1080p 设计稿（战场含空场与复杂状态）＋一组可编辑精绘组件＋一个 Godot 实际渲染样板**。这一步完成后，再锁定整批资源的尺寸与材质，减少卡框和场地的重复制作。

排期按精绘样板通过后重新估算；全量像素重绘、四页精修与完整玩法页面的工作量不同，不能用既有基础交付的时间推算整轮。

## 9. 验收标准

- 设计与工程：默认与回退行为明确；1920×1080 为主稿，1280×720、1600×1000 为兼容稿；不拉扁背景，不让保存的显示设置失效。
- 文字：实际渲染逐项检查卡面安全区、长卡名、数值、tooltip、完整详情和弹窗；文字与宝石/边框没有重叠，输入中文不被截断。
- 美术：关键资源有可编辑分层源稿、共享调色板和版本记录；导出与源稿一致；像素密度、材质光源及采样稳定。
- 状态：普通、悬停、按下、焦点、禁用可辨；选中、合法候选、目标和成本选择各有图形差异；错误、空态、等待与保存失败具备实际落点。
- 战场：空场和复杂场面均清楚；牌库、副卡组、灰烬、阵法、解析、施法、手牌一眼可定位；详情或连锁浮层不会遮住当前必须执行的操作。
- 交互：拖动命中与视觉相符，取消返回；确认前不支付；旧决策回调不会作用于新决策；隐藏牌、交接遮挡和匿名效果无泄露。
- 实机：Windows 100%/125%/150% DPI、窗口/全屏、IME、失焦、长文本与大手牌验证；复杂场面的性能记录给出硬件、时长和帧时间，不以短时截图代替。
- 证据：每批保存 Godot 实际截图、资源校验和必要回归结果。静态概念稿、HTML 预览、引擎展示与完整玩法验收分别标记。
